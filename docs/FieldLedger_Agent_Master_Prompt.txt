PRODUCT OVERVIEW
Product name: FieldLedger — Farm Business Tracker.
Purpose: A simple, mobile-first daily ledger for recording production/sales, labour and operating expenses for two separate farm-related products. The main users need to enter data quickly from an Android phone, review monthly performance, and download/share statements. A responsive desktop web experience must remain useful too.

Two separate workspaces:
A. Brinjal — கத்திரிக்காய். Use a violet/purple theme. The key unit is bags, each of which has its own weight, brinjal type/category, and size. Rates are entered per kg and can vary by day. Labour is tracked separately for men and women.
B. Muskmelon — முலாம்பழம். Use a yellow/amber theme. The main quantity is kilograms; income is quantity × rate/kg. The overview/dashboard emphasis must be monthly, not a daily-statistics-first dashboard. Daily transactions and date-wise monthly reporting are still needed. Use a recognizable muskmelon/cantaloupe icon, not a coconut icon. The prototype currently includes a custom SVG melon icon; preserve or improve it.

Brinjal overview may show recent daily activity and monthly performance. Muskmelon overview should primarily show month-level performance and month navigation.

3. Records: list saved daily records for the selected product, newest first; enable view/edit/delete and preferably date/month filtering or searching. Empty states must explain how to add the first record.

BRINJAL DAILY ENTRY — DETAILED REQUIREMENTS
Fields/behaviour:
- Date of record.
- Number of bags: dropdown/selector. When a user selects N bags, immediately open a bag-details modal containing exactly N numbered bag sections. For example, selecting 5 bags must display Bag 1 through Bag 5, not one aggregate weight field.
- Every bag section has exactly these inputs: (1) Weight in kg, (2) Brinjal type/category dropdown, (3) Brinjal size dropdown with S, M, L. Type choices must be read from Settings and changes in Settings must appear in new/edit bag modals.
- Each bag row must be independently editable. If the user reopens “View / edit bag details” before saving the full day, previously entered values must still be present. Save in the modal updates the daily-entry draft but must not prematurely save the full daily record. Cancel/close should not silently destroy already saved-to-draft values; define clear cancel semantics.
- Changing bag count after details have been entered must not silently lose data. Preserve the first N details when increasing/decreasing the count, show a confirmation before removing bag rows if the count is reduced, and clearly tell the user what will be removed.
- Total weight = sum of each bag's weight. Bag count should match the number of saved bag-detail rows. Do not allow a count/details mismatch.
- Rate per kg: editable for each daily record because the market rate can vary each day. Sale/gross value = total weight × rate per kg.
- All numeric inputs must validate as non-negative numbers; do not allow NaN/undefined values to leak into calculations. Allow decimals for weight and rate where appropriate; currency rounding/formatting must be consistent.

BRINJAL LABOUR
- Provide separate count dropdowns for Men and Women. Zero must be selectable. Use a sensible range and make it easy to change.
- Provide a separate editable per-person daily wage input for men and women.
- Labour salary = (men count × men's wage) + (women count × women's wage).
- Example acceptance calculation: 5 men × ₹500 + 5 women × ₹400 = ₹4,500 labour salary.
- Show men's count, men's wage and subtotal, women's count, women's wage and subtotal where appropriate. The combined labour salary must be visible in the daily summary and monthly report.
- The source sheet only supplies total labour count and total labour salary for historical rows, not a men/women split. Do not pretend the historical split is known. Current prototype seeds historical counts into the men field to retain the aggregate count for sample/demo purposes. Make this limitation clear in code or migration notes, or represent migrated legacy labour as aggregate/unclassified if the architecture allows. Ask the owner before transforming real production data.

BRINJAL EXPENSE MODAL
- “Add expense details” / “View-edit expense details” opens a modal containing a list of line items.
- Each expense item has exactly: Date (defaults to today's local date), “What for?” / purpose, Amount in Indian Rupees (₹), and optional Notes.
- Include an “Add another expense” button that appends another full, independently editable item. Allow removing a line item with a clear affordance.
- Saving the modal returns to the daily-entry form and displays the aggregate expense amount. Reopening before saving the full day must show the draft line items and their values.
- Expense total = sum of all line-item amounts. Validate purpose and amount as required; notes are optional.
- Preserve each expense line's own date. Monthly reporting must apply a clearly defined rule. Preferred accounting rule: expense report totals are grouped by each expense item's own date, while a daily record may show all expense items linked to that record. Document this distinction so monthly totals do not double-count or attribute an expense to an unintended month. If you choose a simpler alternative, state it and make the UI/date semantics consistent.
- When editing an existing daily record, expense items must load with their date, purpose, amount and notes, and changes must persist on save.

BRINJAL SUMMARY CARDS / CALCULATION RULES
Keep the key metrics visually separate for quick scanning; do not merge every value into one dense panel. At a minimum show:
- Total weight (kg) and bag count.
- Sales / gross value = total bag weight × daily rate/kg.
- Operating expenses = total expense line-item amounts.
- Labour salary = men subtotal + women subtotal.
- Net after recorded costs = gross value − operating expenses − labour salary.
Use Indian locale number formatting and ₹ currency formatting. Keep formulas consistent in daily view, records, monthly reports and exports. Clearly label gross sales separately from net earnings.

MUSKMELON DAILY ENTRY AND MONTHLY-FIRST OVERVIEW
- Daily entry fields: date, quantity in kg, rate per kg, and expense line items using the same expense-modal schema (date, purpose, amount ₹, optional notes, multiple line items). No brinjal bags, brinjal type/size or labour fields unless explicitly requested later.
- Gross income = quantity kg × rate/kg.
- Net after recorded costs = gross income − operating expenses.
- The Muskmelon overview should make month-level totals and month selector/navigation the primary interaction; do not present it as a daily production dashboard identical to Brinjal. Still provide daily record entry, records, and date-wise monthly statements.
- Use independent data and independent month totals for Muskmelon; switching products must never mix business results.

MONTHLY REPORTS AND EXPORTS
- Month selector and date-wise sorted rows (oldest-to-newest in statement, newest-first in Records list).
- Brinjal statement should contain date, bag count, total weight, rate/kg, gross sales, operating expenses, men count, women count (or a clearly handled legacy total), labour salary and net after costs. Include monthly totals for weight, bags, gross, expenses, labour salary and net.
- Muskmelon statement should contain date, quantity (kg), rate/kg, gross income, operating expenses and net after costs, with monthly totals.
- Keep the source spreadsheet's historical sample values recognizable. The source column called “Profit” for Muskmelon mathematically represents quantity × rate before expenses; label it “Gross Income” in the improved UI and show net after expenses separately.
- Provide working downloads for: monthly PDF (browser print flow is acceptable for the prototype; show clear instructions to choose Save as PDF), Excel `.xlsx`, CSV, monthly PNG statement, and complete JSON backup. PNG should be a readable, formatted statement and on supporting mobile browsers may use the share sheet for saving to Gallery/Photos.
- JSON import must validate the file shape, request confirmation before replacing existing data, handle malformed files gracefully, and give success/failure feedback. JSON export should contain products, expense details, settings and profile. Keep a clear recovery path for a user who changes device or browser.
- Exports must match the selected product and month, include correct totals and currency/units, and use readable filenames (e.g. `fieldledger-brinjal-2026-10.xlsx`). Do not say a file was exported if it was not.

DATA MODEL AND RELIABILITY
- Keep Brinjal and Muskmelon records isolated in separate collections/tables.
- Suggested daily record shape: id, date, ratePerKg, bagDetails[] for Brinjal, menCount, womenCount, menWage, womenWage, expenseItems[], createdAt/updatedAt. Muskmelon uses id, date, kg, ratePerKg, expenseItems[], createdAt/updatedAt. Use stable unique IDs; never use display index alone as an ID.
- Bag object: id (recommended), weightKg, brinjalType, size. Expense object: id, date, purpose, amount, notes.
- Settings: theme, text size, brinjalTypes[]. Profile: farm/workspace name, owner name, phone, location. Avoid embedding unnecessary personal information in logs or exports.
- Existing prototype is plain HTML/CSS/vanilla JavaScript and uses browser localStorage (`fieldledger-prototype-v1`) for persistence. It has no configured database, API, authentication, cloud sync or production backend. Treat localStorage persistence as prototype-only unless the owner asks for a production architecture.
- If migrating to a framework/backend, first state the proposed stack and why, preserve current behaviours, create a migration plan for existing prototype/local data, and do not silently break JSON backups. Do not claim cross-device sync unless implemented and verified.
- Add input validation, safe output escaping, error handling and storage quota handling. Guard against malformed localStorage/backup values. Confirm destructive operations. Do not lose unsaved draft values on accidental navigation without warning.
